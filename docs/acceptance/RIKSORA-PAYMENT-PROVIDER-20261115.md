# RIKSORA — payment provider abstraction and DOKU adapter design (2026-11-15)

Status: design plus tested pure code. **DOKU is NOT integrated or tested against DOKU; no credentials exist; no real payment is possible.** Midtrans (`cloud/midtrans.py`, `cloud/billing.py`) is untouched.
- Contract: `cloud/payment_provider.py` (PaymentRequest, VerifiedEvent, PaymentProvider, deterministic `next_state` transition rule: duplicate ignored, lower-precedence event never overwrites a terminal one, late PAID after EXPIRED becomes HOLD for manual reconciliation, REFUNDED/CHARGEBACK win). The ledger will be updated only from a VerifiedEvent, idempotently by `(provider, event_key)`.
- Adapter: `cloud/doku.py` from DOKU's public documentation (signature = HMACSHA256 over Client-Id, Request-Id, Request-Timestamp, Request-Target, Digest lines; digest = base64 SHA-256 of the body, POST only; verification of notifications with the notification URL path as Request-Target; Checkout create `POST /checkout/v1/payment` with order.amount, order.invoice_number, payment.payment_due_date). Tests `tests/test_payment_provider.py` 5 PASS use vectors computed from the documented algorithm with a fake secret, not DOKU's samples.
- Open points the documentation does not settle (confirm in the DOKU sandbox before use): digest over exact transmitted bytes; Checkout Request-Target path (inferred); timestamp tolerance (none documented, replay guard is Request-Id deduplication); inbound Request-Target when an override notification URL is used; expiry notification body and chargeback/dispute notifications (not documented; the adapter maps SUCCESS, FAILED, EXPIRED, REFUNDED, VOIDED, PENDING only); `expired_date` is UTC+7; FAILED is not terminal for Checkout.
- Needed to proceed: sandbox Client-Id and Secret Key in a 0600 file, the merchant's decision DOKU vs Midtrans, a public HTTPS notification URL.
