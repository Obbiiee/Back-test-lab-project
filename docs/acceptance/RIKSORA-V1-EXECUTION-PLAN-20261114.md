## 2. The capacity model (replaces the fixture-based claim)
Load tests so far replayed 2,048 ticks per session. Real sessions are limited by ticks revealed per second per worker. Codex's canonical engine (engine-only, synthetic, one closed trade per run, `AI_CONTEXT/04_CURRENT_PHASE.md`) measured 656-714 ticks/s per core (65,536 ticks in 91.7 s; 262,144 in 399 s; 524,288 in 772 s) with a peak process RSS of only 197-310 MiB; our reference reducer measured 256-1,236 ticks/s (event-dense to event-sparse); the Claude jump engine skips quiet stretches (65,536 sparse ticks in 0.07 s) but is only about 4.5x faster on an order-dense scalping scenario. EURUSD averages about 1.1 ticks per weekday-second (2.16 M ticks per month).
Little's law: workers busy = (traders playing) x (playback speed) x (1.1 ticks/s) / (ticks/s per worker). Example with 700 ticks/s per worker: one worker serves about 10 traders at 60x average (peak about 2 traders at 5x burst density); 4 workers about 40 traders at 60x average, far fewer at 1,000x. These are ESTIMATES: the real value of ticks/s per worker on real-month sessions is the single most important unmeasured number, and the product's frozen per-command limits (256 steps of 64 timestamp groups) plus the 30 s native deadline must be shown to hold on a real month (an earlier checkpoint of the product refused a 65,536-tick durable replay with `REFUSED_RECOVERY_LIMIT`).

## 5. Test rules (all new measurements)
Open-model arrivals plus closed-loop; >= 5 runs per gate with median/min/max; warm and cold separated; candidate order alternated; raw JSON/CSV, exact command, dataset manifest SHA and commit SHA stored; only one measurement at a time on the VPS; cgroup budget 5 vCPU / 14 GiB with OS-protection gates (owner addendum); results labelled proven / hypothesis / prototype / needs production-like acceptance; synthetic and real (rights UNKNOWN, private QA) kept apart.

## 6. Economics model (inputs to fill; no invented prices)
Monthly cost = VPS + R2 (user data) + payment fees + data license (postponed). Capacity inputs: peak concurrent sessions C (proven today: 15 clean, target 20), active hours per user h, peak factor p (assumed 4): registered users per VPS = C / (p x h / 720). Per-user VPS cost = VPS price / registered users. Worked example, VPS EUR 33 and h = 20: C = 15 gives about 135 users and about EUR 0.24 per user-month; C = 20 gives about 180 users and EUR 0.18. Data per user (to measure in W1/W6): database growth per 120-trade session (unmeasured; 0.1-0.2 MB per one-trade journey observed). Product packaging should limit concurrent sessions per user (queue admission already 2 per user) and cap replay speed rather than monthly hours, because cost appears at peaks.
