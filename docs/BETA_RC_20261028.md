## Rollback while writes remain frozen

1. Keep public write admission closed. Stop the candidate service and preserve its database, logs and release directories.
2. Restore the prior API code/config and static release targets from the verified pre-switch snapshot. The static command above only reverts frontend files; it does not restore the API or database.
3. If migrations were applied, bind the previous application to the separately restored pre-switch recovery database. The strict runtime guard compares the complete migration ledger, so an older runtime cannot be assumed to accept the newly migrated database even when individual constraint changes are additive. Do not remove migration ledger rows or weaken the guard to force startup.
4. Start the previous release using its restricted role, verify its exact migration fingerprint, HTTPS account routes and saved Session/journal consistency, then reopen writes. Keep the candidate database for investigation; never overwrite it with the backup.
5. If any real customer writes were accepted after the switch, a pre-switch database rollback would omit them. Freeze admission and retain both databases; use a reviewed forward fix or a separately approved canonical reconciliation before reopening. Do not automatically restore an old backup over current customer data.
